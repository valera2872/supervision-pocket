# Supervision Pocket 0.10 — защищённая связь психолога и супервизора

## Цель версии

Версия 0.10 должна заменить ручную передачу `.sprequest` основным сценарием:

1. супервизор создаёт приглашение;
2. психолог принимает его в приложении;
3. психолог передаёт выбранный запрос;
4. запрос появляется во входящих супервизора;
5. супервизор может изменить статус и отправить уточняющий вопрос;
6. обе стороны видят историю передачи;
7. любая сторона может отозвать соединение.

Файл `.sprequest` остаётся резервным офлайн-каналом.

## Выбранная платформа

Для первой серверной беты используется Supabase:

- Flutter SDK;
- PostgreSQL и миграции в репозитории;
- Row Level Security для доступа только участников связи;
- Realtime для появления новых запросов без ручного обновления;
- европейский регион при создании проекта;
- возможность позднее вынести сервер или мигрировать данные без переписывания модели из NoSQL.

Приложение не должно зависеть от Supabase в доменной логике. Сетевой репозиторий подключается через интерфейс, а шифрование выполняется до вызова API.

## Модель угроз

Защищаемся от:

- ошибочного доступа другого пользователя приложения;
- ошибки в клиентском запросе или фильтре;
- просмотра открытого текста в панели базы данных;
- утечки резервной копии базы;
- подмены зашифрованного пакета между разными запросами;
- повторного использования просроченного приглашения.

Не обещаем защиту от:

- скомпрометированного телефона;
- снимка экрана или ручного копирования получателем;
- вредоносной клавиатуры и системной службы распознавания речи;
- пересылки ссылки-приглашения третьему лицу до принятия;
- сохранения уже расшифрованного материала получателем после отзыва связи.

Последний пункт принципиален: отзыв доступа блокирует новые обращения к серверу, но не может удалить сведения, которые второй участник уже законно получил и сохранил.

## Принцип слепого сервера

Сервер получает только:

- идентификаторы пользователей и связи;
- даты и статусы;
- номер версии ключа;
- nonce, ciphertext и MAC;
- технический журнал событий без содержания запроса.

Сервер не получает:

- ключ связи;
- псевдоним случая;
- наблюдаемый эпизод;
- интерпретацию и реакцию психолога;
- рабочую гипотезу;
- вопрос супервизору;
- комментарии участников.

Все содержательные поля сериализуются в JSON и шифруются на устройстве AES-256-GCM.

## Приглашение и обмен ключом

Супервизор создаёт:

- случайный одноразовый токен приглашения;
- отдельный случайный 256-битный ключ связи.

На сервер отправляется только SHA-256 токена. Ключ связи остаётся на устройстве.

Ссылка имеет форму:

```text
https://app.example/join?invite=<одноразовый-токен>#key=<ключ-связи>&v=1
```

Часть после `#` не отправляется обычным HTTP-запросом на сервер. Приложение извлекает её локально и сохраняет ключ в Android Keystore через `flutter_secure_storage`.

Токен и ключ выполняют разные задачи:

- токен позволяет один раз принять приглашение;
- ключ шифрует содержательные данные связи.

Сервер видит токен только при принятии и никогда не видит ключ.

## Привязка шифротекста к контексту

При шифровании используется Additional Authenticated Data:

```text
supervision-pocket|connectionId|objectId|schemaVersion|keyVersion
```

Это означает, что пакет нельзя незаметно:

- перенести в другую связь;
- выдать за другой запрос;
- открыть как другую версию структуры;
- расшифровать после подмены версии ключа.

## Что синхронизируется в 0.10

Синхронизируется:

- выбранный запрос на супервизию;
- его технический статус;
- зашифрованные уточняющие сообщения;
- факт получения и изменения статуса;
- отзыв связи.

Не синхронизируется:

- весь архив случаев психолога;
- черновики;
- личные заметки психолога;
- личная подготовка супервизора;
- остальные записи по случаю;
- PIN приложения;
- локальные ключи хранилища.

Передача всегда начинается с явного выбора конкретной карточки.

## Таблицы первой серверной беты

### `profiles`

Минимальный профиль пользователя: имя для отображения и профессиональная роль.

### `connection_invitations`

Одноразовые приглашения. Хранится хеш токена, срок действия и состояние использования.

### `supervision_connections`

Связь конкретного супервизора и супервизанта, состояние доступа и версия ключа.

### `shared_requests`

Зашифрованные пакеты запросов. Открытых профессиональных текстов в колонках нет.

### `request_messages`

Зашифрованные уточняющие вопросы и ответы по запросу.

### `connection_audit_events`

Технический журнал: создание запроса, изменение статуса, сообщение, принятие и отзыв связи. Содержание сообщений не записывается.

## Авторизация базы

Row Level Security проверяет:

- пользователь является участником активной связи;
- отправитель запроса совпадает с текущим пользователем;
- связь запроса и комментария совпадает;
- содержательную часть запроса может заменить только отправитель;
- идентификаторы связи, отправителя и дата создания неизменяемы;
- приглашение может просматривать и отзывать только создавший его супервизор.

Принятие приглашения и отзыв связи выполняются через ограниченные SQL-функции `security definer` с фиксированным `search_path`.

## Уведомления

Push-уведомление не содержит профессионального текста. Допустимые сообщения:

- «Получен новый запрос на супервизию»;
- «Супервизор задал уточняющий вопрос»;
- «Изменён статус запроса».

Текст становится доступен только после открытия и разблокировки приложения.

## Ограничения первой беты

### Одно основное устройство на пользователя

Ключ связи хранится только на устройстве, принявшем или создавшем приглашение. Перенос на второе устройство в 0.10 не поддерживается.

### Нет восстановления ключа сервером

Потеря устройства означает потерю доступа к старым зашифрованным материалам, если пользователь не создал локальную защищённую резервную копию.

### Нет криптографического удаления у получателя

После расшифровки получатель может сохранить текст. Отзыв соединения прекращает будущий сетевой доступ, но не отменяет уже состоявшуюся профессиональную передачу.

## Критерии готовности 0.10

Версия не считается готовой, пока автоматические тесты не подтверждают:

1. правильный ключ открывает пакет;
2. другой ключ не открывает пакет;
3. изменение `connectionId` или `objectId` делает пакет недействительным;
4. пользователь вне связи не видит строки базы;
5. отозванная связь не получает новые данные;
6. в серверных таблицах, логах и push-сообщениях нет открытого текста кейса;
7. старый файловый способ передачи продолжает работать.
